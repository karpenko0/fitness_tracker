# SPEC-001. Product Vision & Scope
**Версия:** 1.0
**Статус:** Ready for development
**Зависимости:** SPEC-002, SPEC-012, SPEC-014; для пользовательских модулей также SPEC-016.

## 1. Назначение и границы
Границы продукта, тарифы, роли и релизный контур.

В документ включён контракт MVP. Функции, не указанные явно, не считаются частью обязательной поставки.

## 2. Участники и user stories
| Роль | Ответственность |
|------|-----------------|
| Product owner | Выполняет основные действия в модуле в рамках назначенных прав |
| Backend API | Валидирует запросы, права, владение данными и сохраняет изменения атомарно |
| Mini App / Admin UI | Показывает состояние операции, ошибки и актуальные данные |

### User Stories
- Как пользователь, я хочу пользоваться возможностями модуля «Product Vision & Scope», чтобы получить ценность без лишних действий.
- Как product owner, я хочу видеть только разрешённые мне действия, чтобы данные и настройки оставались защищёнными.
- Как пользователь с нестабильной сетью, я хочу получить понятный результат операции или сообщение об ошибке, чтобы не потерять данные.

## 3. Функциональный сценарий

1. Клиент запрашивает доступные данные или форму.
2. Пользователь выполняет действие и подтверждает его.
3. Клиент валидирует обязательные поля и отправляет команду в API.
4. Сервер проверяет сессию, роль и бизнес-правила, выполняет транзакцию.
5. Клиент получает результат, обновляет экран и фиксирует аналитическое событие при необходимости.

## 4. Бизнес-правила

1. Определять MVP и не включать функции следующих этапов без решения владельца продукта.
2. Владелец данных может читать и изменять только собственные ресурсы, если отдельное право не разрешает иное.
3. Справочные значения, enum и лимиты валидируются на сервере; UI-проверка не является защитой.
4. Временные значения хранятся в UTC; отображение и расчёт дня выполняются по timezone профиля.
5. Все значения денег/весов/измерений имеют явную единицу и точность в OpenAPI.

## 5. API-контракты
Все эндпоинты используют JSON, префикс `/api/v1`, UTF-8 и `Authorization: Bearer <accessToken>`. Ошибки имеют формат `{ "error": { "code": "...", "message": "...", "traceId": "..." } }`. Изменяющие запросы из Mini App передают `Idempotency-Key` (UUID). В Swagger определяются схемы, примеры, коды ошибок и RBAC.

### HTTP Коды
| Код | Значение |
|-----|----------|
| 200/201 | Успешное чтение/создание |
| 400 | Некорректные данные |
| 401/403 | Нет сессии / нет права |
| 404 | Ресурс не найден или недоступен владельцу |
| 409 | Конфликт версии или состояния |
| 422 | Правило домена не позволяет операцию |

### Контракты модуля
- `GET /product/config` — публичная конфигурация функций и тарифов

Для list-эндпоинтов используется объект `page, pageSize, total, items`, по умолчанию pageSize=20, максимум 100. PATCH принимает только изменяемые поля и возвращает актуальную версию ресурса.

## 6. Модель данных
- **product_features**: id UUID PK, code UNIQUE, release_stage, enabled
- **plans**: id, code UNIQUE, name, status

### Общие поля доменных таблиц:
- `created_at TIMESTAMPTZ`
- `updated_at TIMESTAMPTZ`
- Внешние ключи индексируются
- Для изменяемых агрегатов применяется поле `version INT` или блокировка на уровне транзакции

## 7. Права доступа
| Действие | Пользователь | Контент-менеджер | Администратор |
|----------|--------------|------------------|---------------|
| Чтение собственных данных | Да | Да | Да |
| Изменение собственных данных | Да | По назначению | Да |
| Изменение системного контента | Нет | Да | Да |
| Просмотр аудита и платежей | Нет | Нет | Да |

## 8. Критерии приёмки

- Согласованы scope MVP, список исключений и матрица Free/Pro; все фичи имеют владельца и этап.
- API возвращает документированные коды ошибок, а не технические stack trace.
- Негативный тест без прав или с чужим `id` не раскрывает данные и завершается 403/404.
- Все изменения, требующие идемпотентности, выдерживают повтор одного запроса.
- Есть unit-тесты доменных правил и интеграционные тесты API; ключевой путь покрыт E2E.

## 9. Наблюдаемость
Логируются `traceId`, пользовательский идентификатор (псевдонимизированно при экспорте), результат команды и длительность. Метрики: error rate, p95 latency, число успешных/неуспешных операций. Административные изменения дополнительно записываются в `audit_logs`.
